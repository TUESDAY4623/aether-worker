
# Project Aether — Phase 1 Implementation Plan

## What We're Building

A distributed AI memory & compute fabric: a **laptop-hosted Controller** (Python) that discovers Android worker devices over the local network, allocates remote memory segments, transfers tensors, schedules work, and runs a small quantized model across devices.

## Implementation Order (following Phase 1 Section 25)

1. **Data structures & config** — Segment, Worker, Message types, constants
2. **Protocol** — Binary framed messages (session ID, type, payload, checksum)
3. **Transport** — TCP server + session management
4. **Device Discovery** — UDP broadcast for worker advertisement
5. **Security** — Pairing flow + session key establishment
6. **Telemetry** — Structured metrics collection + thermal state machine
7. **Memory Manager** — Segment allocation, placement, pinning, release
8. **Tensor Transfer** — Chunked resumable transfer with checksums
9. **Worker Registry** — Worker registration, capability reports, health tracking
10. **Scheduler** — Rule-based scoring (compute, memory, thermal, latency)
11. **Model Partitioner** — Memory-only + layer partitioning modes
12. **API Server** — REST endpoints for runtime integration
13. **Controller app** — Ties everything together
14. **Android Worker** — Minimal Kotlin service
15. **Tests + benchmarks**

## Key Design Decisions

- **Python Controller** with `asyncio` for concurrency (matches Phase 1 spec: "Python reserved for experimentation, tooling, and model orchestration")
- **Binary protocol** over TCP (not JSON) for large tensor payloads, defined with a simple custom framing format (no protobuf dependency for Phase 1 to keep it simple, but structure it so protobuf can be swapped in later)
- **UDP broadcast** for device discovery on the LAN
- **Rule-based scheduler** first (deterministic, easy to benchmark/debug per spec)
- **Large segments** (tens to hundreds of MB) rather than page-level migration
- **Thermal state machine** with graceful degradation, never auto power-off
